# e2e テスト test_large_post_body の flaky を修正する

- Created: 2026-08-15
- Completed: {YYYY-MM-DD}
- Branch: feature/fix-e2e-large-post-flaky
- Polished: 2026-08-15

## 目的

`tests/test_e2e_http3.py` の `test_large_post_body` の flaky を調査し、修正する。テスト全体の実行で確実に通る状態にし、CI の信頼性を高める。closed issue 0034 が同一テストのデータ破損 flaky を修正したが、その後に失敗が再観察されたため、0034 の修正の検証と残存原因の調査を行う。

## 現状

- 2026-08-15 にローカル (macOS) で `uv run pytest tests/ -v --timeout=30` を実行した際、`test_large_post_body` が 1 回失敗した。受信データの内容不一致で、pytest の bytes 比較の失敗出力から不一致位置 (12694 バイト目) が観察された。失敗ログは保存されておらず、どの assert (サーバー受信側・クライアント受信側) で失敗したかも未確認
- その後、単体 9 回・全体テスト 3 回 (develop ブランチ)・全体テストの再実行 1 回では再現しない (観察は 1 回のみ)
- テストは QUIC 経由で 32KB のデータを送受信する実通信 E2E で、データは `bytes((index % 256) for index in range(32 * 1024))` の周期性のあるパターン。assert は 2 箇所 (サーバーが受信したボディ・クライアントが受信したエコー)
- closed issue 0034 (2026-08-07 完了) は、この同一テストの「データの欠落・重複 (ペイロード破損)」を `src/bindings/quic.cpp` の `QuicConnection::send()` の WRITE_MORE 契約違反の修正で解決した。0034 はローカルで再現しないまま「再現率の低下も許容」で完了しており、本 issue の観察 (データ内容の不一致) はその修正後のもので、0034 の修正が不完全だった可能性の検証を含む

## 設計方針

- 原因の切り分けは次の順で進める:
  1. 0034 の修正対象 (`QuicConnection::send()` の `more_used` フラグ・WRITE_MORE 契約周辺) の再検証。修正後の現行実装で同じ経路の欠落・重複・順序入れ替えが残っていないか確認する
  2. QUIC / HTTP/3 層のデータ整合性 (パケット喪失 (RFC 9002 Section 6)・再送 (RFC 9000 Section 13.3)・フロー制御 (RFC 9000 Section 4.1)・STREAM フレームのオフセット処理 (RFC 9000 Section 2.2 / 19.8)・HTTP メッセージのフレーミング (RFC 9114 Section 4.1))
  3. テストのタイミング依存 (イベントの順序・バッファ処理)
- 観察された症状 (データの内容不一致) は、0034 で修正されたデータ欠落・重複と同系統の可能性が高い。欠落単独はテストの構造上タイムアウトとして観察される (受信完了イベントが発火せず応答が送られない) ため除外でき、内容不一致は重複・順序入れ替え・欠落と重複の同時発生で説明される
- 調査手段: pytest の bytes 比較は不一致位置とその位置の 1 バイトの値のみを表示し、値の全体は省略するため、失敗時に期待値と実値の不一致箇所を完全に出力するようテストの assert を強化してから、単体と全体の両方で繰り返し実行する (全体実行時の負荷条件が再現条件の可能性があるため、シェルループ等で回す)。どちらの assert (サーバー受信側・クライアント受信側) で失敗したかを記録する (pytest の失敗出力は assert の行番号を含む)。テストデータは 256 バイト周期のため、256 バイトの倍数のズレは bytes 比較で検出できない検出限界がある (必要に応じて 256 と互いに素な周期に変更する)。強化した assert (詳細な不一致メッセージ) はそのまま回帰テストとして残す
- 原因特定後に修正し、回帰テストを追加する
- 原因が特定できない場合: 調査結果 (確認した経路・再現条件・残った仮説) を本 issue の「## 解決方法」に記録して完了とする (closed issue 0004 の先例に倣う)
- 変更対象: 原因に応じて `src/bindings/quic.cpp` / `src/bindings/http3.cpp` / `src/webtransport/http3/` / `tests/test_e2e_http3.py` のいずれか。`CHANGES.md` は変更しない (CODEBASE.md の指示)

## 完了条件

- `tests/test_e2e_http3.py` の `test_large_post_body` の assert を強化し、不一致時にどちらの assert か (サーバー受信側 / クライアント受信側)・不一致位置・期待値と実値の該当範囲を出力する。強化した assert は回帰テストとして残す
- テストデータの 256 バイト周期を見直し、256 バイトの倍数のズレでも不一致を検出できるようにする (256 と互いに素な周期にする等)
- 低負荷な再現手段を確立する: 損失を注入できる E2E ハーネス (受信データグラムを選んで落とす等) を用意し、`test_large_post_body` または同等の小さいテストで再現を試みる。注入条件と再現の有無・再現率を記録する
- 原因が特定された場合は、修正内容と根拠が「## 解決方法」に記録され、回帰テストが追加されている
- 原因が特定できない場合は、確認した経路・再現条件・残った仮説が「## 解決方法」に記録されている (closed issue 0004 の先例に倣う)
- 全テストが通過する

## reopened にした理由

- pending にした理由の「再現条件の解明に低負荷な方法 (パケット喪失の強制等) が必要であり、方針の見直しを要する」に従い、方針を見直して再開する。作業を 2 つに分ける: (1) 検出限界の解消 (assert の強化とテストデータの周期見直し) は原因の特定に依存せず実施できる、(2) 低負荷な再現手段 (損失注入) を確立して再現を試みる。(1) を先に実施することで、再現した場合の切り分けが可能になる
- 再開時点の確認: `tests/test_e2e_http3.py` の `test_large_post_body` は現行の develop に存在し、assert は 2 箇所 (サーバーが受信したボディ・クライアントが受信したエコー) のままである。テストデータ `bytes((index % 256) for index in range(32 * 1024))` も 256 バイト周期のままで、256 バイトの倍数のズレを検出できない検出限界も残っている
- 完了条件から「全体テスト 10 回連続 + 単体 50 回連続で失敗しない」を外した。再現率が極めて低く (単体 300 回で再現 0 回の記録がある)、回数を増やすだけの検証は CI 並みの負荷を要するわりに得られる情報が少ないため、再現手段の確立と観測の質 (不一致の完全な出力) を優先する
- `CHANGES.md` を変更対象から外した (CODEBASE.md の指示)

## pending にする理由

- 再現試行のテスト負荷が高く (全体テストの繰り返し実行が CI 並みの負荷になる)、実行を中断した
- 調査 (0034 の修正対象である `QuicConnection::send()` の再検証・QUIC / HTTP/3 層のデータパス・高レベル API) では明確なバグを特定できなかった
- 単体 50 回の再現試行で 1 回再現した (18 回目) が詳細が未取得で、その後の 300 回では再現しなかった (再現率は極めて低い)
- 再現条件の解明に低負荷の方法 (パケット喪失の強制等) が必要であり、方針の見直しを要するため pending とする。再現手順が確定した時点で reopened する
